# Depth-first scope: build the Demo Spine before Peripheral Roles

As a solo developer building a real, scored Topcoder submission in ~30-36 hours against a spec large enough for a small team (5 role dashboards, 3 protocol-shaped adapters, an evidence-gated scoring pipeline, a simulation engine, i18n, and a live deployed playground), spending equal polish on every Must item risks a demo where nothing is polished enough to convince anyone. Every Must item in every role is still built and functionally real — nothing is stubbed or skipped. We decided to spend *extra* polish, first, on the Demo Spine — Passenger Screen, Retailer, Platform Admin, the decision pipeline, and the simulation engine — since a rough or unconvincing decision pipeline kills the required 15-minute "cause and effect in under a minute" demo outright. Media Manager and Airline Representative remain Peripheral Roles: every Must item works and is wired to real generated data, implemented at the simplest correct depth (generic lists/tables rather than bespoke UI), because they aren't on screen during the live demo. The explicitly-marked "Should (proposed)" items (9 total, across all roles) are cut outright — the spec frames these as its own bonus tier, distinct from the "Required WOW features" (GenAI creative assistant, Smart recommendation), which stay in scope but via their spec-sanctioned simplest path (mock-only creative assistant, a plain scoring heuristic for slot recommendations).

This qualifies for an ADR: it's hard to reverse (shapes what gets built first and what ships), surprising without context (a reviewer seeing uneven polish across roles would wonder why), and the result of a real trade-off (breadth vs. depth under solo/deadline constraints).
